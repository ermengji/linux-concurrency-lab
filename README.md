# linux-concurrency-lab

面试和项目里反复被问到的并发基础组件，自己写一遍，并用压测把数字量出来。

不是"手写一个线程池"的教学 demo —— 每个组件都带边界处理、失败路径和可复现的 benchmark，
因为我需要的是能在生产视频流水线里用、且能被追问细节的东西。

## 组件

| 组件 | 文件 | 说明 |
|---|---|---|
| `SpscRingBuffer<T>` | `include/spsc_ring_buffer.hpp` | 单生产者单消费者无锁环形缓冲，容量自动对齐 2 的幂 |
| `LatestFrameBuffer<Frame>` | `include/latest_frame_buffer.hpp` | "永远给最新一帧"的槽位，带丢帧计数与序号去重 |
| `ThreadPool` | `include/thread_pool.hpp` | 固定大小线程池，`std::future` 取结果，支持优雅收敛 |

三者组合起来就是一条视频流水线的骨架：

```
 capture thread          inference threads            reporter
      │                        ▲                         ▲
      │ publish(frame)         │ acquire(latest)         │
      ▼                        │                         │
 ┌──────────────┐      ┌───────────────┐        ┌──────────────┐
 │LatestFrameBuf│─────▶│ inferred queue│───────▶│  bounded Q   │
 └──────────────┘      └───────────────┘        └──────────────┘
   丢帧而非排队            多 worker 并行            背压/丢弃策略
```

## 构建与运行

```bash
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release
cmake --build build -j
ctest --test-dir build --output-on-failure

./build/bench_ring 20000000
./build/bench_pool 200000
```

只依赖 C++17 和 pthread，没有第三方库。

## 实测数据

环境：32 核 x86_64，gcc 13.3，Release（-O3），每项取 5 轮最好值。

### SPSC 环形缓冲（2000 万次，单生产者 + 单消费者）

| 容量 | ns/op | Mops/s |
|---|---|---|
| 64 | 5.70 | 175.6 |
| **1024** | **2.50** | **400.2** |
| 65536 | 2.78 | 359.7 |

2.5 ns 一次传递约为 7 个 CPU 周期，基本贴着一个 `store` + 一次缓存行同步的下限。

容量 64 反而更慢，是因为缓冲太小，生产者经常等消费者腾位置，实际退化成两者交替阻塞；
容量 65536 略慢于 1024，是缓冲跨了更多缓存行，局部性变差。

### 线程池（20 万个只做一次整数加法的任务）

| workers | tasks/s | us/task |
|---|---|---|
| 1 | 1,605,125 | 0.623 |
| 2 | 1,438,045 | 0.695 |
| 4 | 486,321 | 2.056 |
| 8 | 524,164 | 1.908 |
| 16 | 498,227 | 2.007 |

## 一个反直觉的结论：线程越多越慢

上表里 **1 个 worker 最快，加到 4 个反而慢 3 倍**。这不是 bug，是任务粒度过小时的必然结果：

1. **现象**：任务本身只有一次 `fetch_add`（约 1 ns），而一次锁争抢 + 唤醒的开销在几十 ns 量级。
2. **原因**：任务队列是全局 `mutex`，提交侧串行加锁，执行侧所有 worker 抢同一把锁。
   线程越多，锁冲突和上下文切换越严重，并行收益被完全吃掉，还要额外付出缓存行在核间
   来回迁移的成本。
3. **边界**：只有当单任务耗时明显大于 (锁开销 + 唤醒开销) 时，加线程才有正收益。
   经验上这个临界点在单任务几百纳秒到几微秒之间，取决于任务队列的实现。

**这是压测才能发现的东西，凭直觉写不出来。** 我把它原样留在仓库里，而不是把任务加重
让曲线变好看。

真实的视频推理场景里，单帧推理是毫秒级，远超这个临界点，所以线程池在那里是划算的 ——
这正是我把 benchmark 和实际用法分开测的原因。

## 设计取舍

**为什么 SPSC 不用 CAS 循环？**
单生产者单消费者时，`head_` 只由生产者写、`tail_` 只由消费者写，没有两个线程写同一个
变量的情况，因此一次 `store(release)` 就够了。用 CAS 是多余的，还会引入失败重试和
ABA 风险。

**为什么要 `alignas(64)`？**
`head_` 和 `tail_` 若落在同一条缓存行，生产者的写会让消费者侧的缓存行失效，即使两者
逻辑上无关 —— 这就是伪共享。分开到两条缓存行后，跨核通信只发生在真正的数据传递上。

**为什么缓存对端索引？**
每次 `try_push` 都 load 一次 `tail_` 会持续访问另一条缓存行。缓存一份 `tail_cache_`，
只在"可能满了"时才去读真值，把绝大多数操作留在本地缓存行里。

**为什么 `LatestFrameBuffer` 反而用 mutex？**
因为它的载荷是一整帧（几百 KB），不是指针。做成无锁需要用 seqlock，而 seqlock 在写冲突
时要整帧拷贝重试，代价远高于一次 mutex。发布频率受限于摄像头（几十 Hz），临界区极短，
锁竞争可以忽略。**这里省下的复杂度比省下的那点延迟更值钱。**

**为什么 `shutdown` 默认 drain？**
"进程要退了就把队列里的事件丢掉"是很多线上事故的来源。默认把已入队的任务做完再退出，
需要立即放弃时才显式传 `false`。

## 已知限制 / 后续

- `ThreadPool` 的全局队列是上面那组数据的瓶颈。后续可做：批量提交（一次加锁入队多个任务）、
  或每线程独立队列 + work stealing。
- `SpscRingBuffer` 要求 `T` 可默认构造；存大对象建议存指针或槽位索引。
- 没有实现 MPMC（多生产者多消费者），按需再加。
